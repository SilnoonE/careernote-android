# 개선 사례: 문제에서 검증 기준까지

아래는 개발 대화에서 발견하고 수정 방향을 정한 사례입니다. 과거 검토 당시의 문제와 학습 포인트이며, 현재 공개 스냅샷 전체의 회귀 테스트 통과를 뜻하지 않습니다.

## 1. 즐겨찾기와 연결 데이터 보존

**사용자 행동:** 지원 기록의 즐겨찾기를 변경합니다.

**검토에서 발견한 원인:** 기존 행 갱신에 INSERT OR REPLACE를 사용하면 부모 행 삭제 동작이 연결된 면접·상태 이력의 CASCADE 삭제로 이어질 수 있었습니다.

**개선 방향:** 즐겨찾기와 수정 시각만 UPDATE하도록 분리했습니다. 다른 편집도 오래된 화면 객체 전체를 덮어쓰는 대신 필요한 필드만 갱신하는 것이 안전합니다.

**회귀 기준:** 상태 이력·면접·질문을 가진 지원 기록의 즐겨찾기를 반복 변경해도 모든 연결 ID와 내용이 유지되어야 합니다.

## 2. 합격률의 의미

**사용자 행동:** 관심 등록, 실제 지원, 합격, 취소, 입사 완료로 상태를 변경합니다.

**검토에서 발견한 원인:** enum의 나열 순서를 단계의 의미로 사용하면 취소가 합격으로 집계될 수 있었습니다. 현재 상태만 보면 합격 후 취소의 과거 결과도 잃습니다.

**개선 방향:** 명시적인 상태 정의와 상태 이력을 활용합니다. 실제 제출 여부·시점, 단계별 결과, 현재 진행 상태를 구분합니다.

**회귀 기준:** 관심→취소는 실제 지원이 아니며, 지원 완료→취소는 제출 이력이 남아야 합니다. 결과 없음은 합격률 0%와 구분합니다.

## 3. D-Day와 달력 날짜

**사용자 행동:** 오늘 또는 내일 마감하는 일정을 확인합니다.

**검토에서 발견한 원인:** 남은 밀리초를 24시간으로 나누면 내일 마감을 오늘로 표시할 수 있습니다. 시각이 섞인 날짜 비교는 당일 항목을 조기에 제외할 수 있습니다.

**개선 방향:** LocalDate와 달력 일수 차이를 사용합니다. 계산 결과를 캐시할 때 오늘 날짜와 시간대 변화도 반영해야 합니다.

**회귀 기준:** 오늘 D-Day, 내일 D-1, 어제 마감. 자정 통과·앱 복귀·서머타임 경계에서도 일관돼야 합니다.

## 4. 저장 함수와 UI 완료의 차이

**사용자 행동:** 긴 기록을 입력하고 저장합니다.

**검토에서 발견한 원인:** 함수 내부에서 별도 코루틴을 시작하면 호출자가 저장 완료를 기다린다고 생각해도 실제로는 먼저 돌아갈 수 있습니다. 필수값 검증 실패 후 화면이 닫히는 흐름도 발견했습니다.

**개선 방향:** 저장 결과를 명시적으로 반환하고 성공 후 이동합니다. 버튼 활성화 조건과 실제 검증을 통일합니다.

**회귀 기준:** 저장 실패 시 입력 보존, 재시도 제공, 빠른 두 번 클릭 시 중복 저장 방지.

## 5. 제출본은 요약이 아니다

**사용자 행동:** 지원한 회사에 제출한 자소서를 나중에 확인합니다.

**검토에서 발견한 원인:** 초기 스냅샷이 앞부분 50자나 제목·버전만 저장해 전체 제출본을 복원할 수 없었습니다.

**개선 방향:** 전체 본문과 문항을 JSON으로 저장하고 원본과 독립적으로 열람하도록 확장했습니다.

**회귀 기준:** 원본 내용을 바꾸거나 삭제해도 제출 당시 전체 텍스트와 필요한 첨부를 볼 수 있어야 합니다. 이전의 잘린 기록을 완전한 제출본으로 표현하지 않습니다.

## 6. 백업 성공보다 복원 실패가 중요하다

**사용자 행동:** 다른 기기 또는 재설치 후 백업을 복원합니다.

**검토에서 발견한 원인:** 검증 전 원본 삭제, 폴더의 비재귀 복사, 롤백 실패 후 사본 삭제 등의 문제가 여러 검토 단계에서 드러났습니다.

**개선 방향:** 임시 위치 검증과 실제 Room 열기, 복구 사본 보존, 파일 및 설정의 함께 복원, 중단 후 복구를 요구했습니다.

**회귀 기준:** 잘못된 파일, 공간 부족, 복사 실패에서도 기존 데이터 또는 검증된 복구 사본이 남아야 합니다.

## 7. 문서별 초안의 동시성

**사용자 행동:** 여러 문서를 번갈아 작성하고 앱을 종료합니다.

**검토에서 발견한 원인:** 공용 초안 하나는 다른 문서와 섞입니다. 문서별 키를 추가해도 오래된 전체 맵을 덮어쓰면 다른 초안을 잃을 수 있습니다.

**개선 방향:** 초기 로딩을 구분하고 개별 문서 갱신을 저장소 경계에서 원자적으로 처리합니다. 자동 저장과 최종 저장의 순서도 통제합니다.

**회귀 기준:** 신규·수정 초안 복원, 교차 저장, 빈 내용 저장, 최종 저장 직후 재진입에서 내용이 보존돼야 합니다.

## 8. 기능 보고와 검증 증거

구현 보고에서 완료로 표시된 항목을 화면과 호출 경로에서 재확인했습니다. 데이터 모델만 존재하거나 버튼에 동작이 연결되지 않은 경우는 부분 구현으로 분류했습니다.

빌드 성공은 컴파일·패키징의 증거입니다. 실제 복원 성공, 예외 경로, 권한, 기기 재부팅, 사용자 데이터 보존을 증명하는 테스트는 별도로 필요합니다.
